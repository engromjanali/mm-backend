Notice notifications

A newly created notice sends after its database transaction commits. Updates and pins do not send another notification. The manager's selected season determines the target: `topic_seasonId_<season_id>`. Title: `New Notice`; body: the notice title (long UTF-8 titles are shortened to fit FCM payload limits).

Setup:

1. Install backend requirements and run `python manage.py migrate`.
2. Set `FIREBASE_SERVICE_ACCOUNT_JSON` locally and on Vercel to the same base64-encoded service-account JSON for the mobile app's Firebase project. Generate it using the command in `.env.example`; paste its output without quotes. Plain JSON and JSON-encoded strings remain supported. Base64 is encoding, not encryption; keep the real value and key file secret and out of committed source. No key file path is needed at runtime. If the variable is empty, Firebase falls back to Application Default Credentials. Enable the Firebase Cloud Messaging API.
3. On iOS, upload the APNs authentication key in Firebase and use a provisioning profile with Push Notifications enabled. Install updated Flutter/CocoaPods dependencies before building.
4. Test on a configured Android/iOS device, grant notification permission, log in, and publish a notice as manager. Verify active members receive it, then disable/leave a member and publish again while that member's app is closed.

The mobile app registers on login, profile changes, startup and resume; refreshed registration tokens are synchronized. Failed registration and invalid topic responses preserve the last confirmed topics and retry after 5 seconds, backing off to a maximum of 60 seconds while the app is active. Retries stop on backgrounding, logout and disposal; resume triggers another sync. Before the first successful registration, no topic subscription is assumed. Subscription topics are derived by the authenticated backend from the active membership in the user’s selected current season only, never accepted from the client. Logout removes the device and invalidates its FCM token. Before each send the backend reconciles the target topic to exclude inactive/left memberships, departed members (`left_at`), inactive accounts and disabled seasons. A failed removal prevents sending. Tokens are redacted in request logs. Subscription operations happen only when membership topics change. Each eligible device has at most two topics: `topic_seasonId_<current_season_id>` and `topic_messId_<current_mess_id>`. The mess topic is reserved for future features and currently sends nothing. Switching season or mess removes old topics on sync. Notice reconciliation also removes outdated subscriptions and never adds a member back to an unselected season.

Delivery is best effort: provider failures are logged without failing notice creation; there is no background retry queue. Android foreground messages display system notifications through the local notifications plugin; iOS uses native foreground presentation. No in-app snackbar is shown. Foreground notifications also preserve notice-detail tap navigation when tapped after the app is closed. Tapping a notification opens `/notices/<notice_id>` in the notice details screen, including background and terminated launches. Startup checks and login are preserved; the details screen loads the notice through the authenticated API, so inaccessible or deleted notices remain unavailable. Web/desktop push is not enabled by this change.

FCM topics are not an authorization boundary: another modified client can subscribe to a predictable topic directly. This implementation excludes tracked ineligible devices, but confidential notice bodies require direct device delivery or an authenticated content fetch instead of topic payloads. See https://firebase.google.com/docs/cloud-messaging/manage-topic-subscriptions.

If registration returns `PERMISSION_DENIED`, grant the service account used by the key the Firebase Cloud Messaging Service Editor role (`roles/cloudmessaging.editor`) on the Firebase project in Google Cloud IAM. Topic management requires `cloudmessaging.topicSubscriptions.create` and `cloudmessaging.topicSubscriptions.delete`; message delivery requires `cloudmessaging.messages.create`. Topics are created automatically when a device subscribes. Provider subscription failures return a sanitized HTTP 503; invalid/unregistered devices return HTTP 400.

IAM role reference: https://docs.cloud.google.com/iam/docs/roles-permissions/firebasecloudmessaging

Flutter notification lifecycle handling lives in `lib/core/helpers/notification_helper.dart` (`NotificationHelper`): payload validation, foreground system display, local/FCM notification taps, background-open events, terminated launch destinations, and listener cleanup. `main.dart` initializes/starts/disposes the helper; `AppRoutes` only defines routes. FCM itself displays notification payloads in the background.
